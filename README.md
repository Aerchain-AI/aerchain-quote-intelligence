# Aerchain Quote Intelligence Copilot — Prototype

Takes the messy, multi-format quotations a procurement buyer actually receives and turns them
into a comparison they can defend to a stakeholder.

See [`docs/PRD.md`](docs/PRD.md) for the product spec and [`BUILD_PLAN.md`](BUILD_PLAN.md) for
the scope freeze and architecture decisions.

```
CREATE RFx → 30 LINE ITEMS → 5 VENDOR RESPONSES → AI EXTRACTS → AI NORMALIZES
→ AI VALIDATES → EXCEPTIONS → COMPARISON → ASK AI → SCENARIO ANALYSIS
→ AWARD RECOMMENDATION → EVIDENCE + CONFIDENCE
```

## The one architectural decision that matters

**The LLM never does arithmetic that reaches the buyer.**

| LLM | Deterministic code |
|---|---|
| Reading documents (5 formats, including a photographed quote) | Totals |
| Extracting into a fixed schema | Currency conversion |
| Interpreting natural-language questions | Unit conversion |
| Explaining a completed result | Rankings, savings, filtering, constraints |

Every number on every screen comes from `services/api/src/calc/engine.ts`. The copilot routes a
question to one of a fixed set of analyses, the engine computes it, and the model explains the
result it was handed. That is why the numbers are reproducible and the recommendation is
defensible.

## Every figure opens its own derivation

Nothing on screen is a number you have to take on trust. Click any figure — a saving, a total, an
item count, a vendor's column total — and the panel shows the rule that was applied, the arithmetic
step by step, the row-by-row contributions, what was deliberately excluded and why, and a set of
verification checks that recompute the result by a second, independent route.

That panel is generated by `services/api/src/calc/derivation.ts`, which is the same code path that
produced the number. No language model is involved, by design: a figure a buyer is about to award a
contract on cannot be explained by something that might paraphrase it wrongly. If a check fails to
reconcile, the panel says so rather than hiding it.

## Run it

Two commands, no API key, no waiting:

```bash
npm run setup
npm run build && npm start
```

Open **http://localhost:4000** and sign in as any profile (the PIN is shown on screen).

A pre-extracted database ships with the repository. On first boot the server restores it, so the
comparison grid, the award recommendation and every derivation are populated immediately. None of
that needs a model — those screens read SQLite and the deterministic engine.

### Live extraction (optional)

Uploading a new quotation is the only thing that calls an API. To enable it:

```bash
cp .env.example .env     # add GEMINI_API_KEYS=<comma-separated keys>
```

Free keys come from [aistudio.google.com](https://aistudio.google.com) → Get API key. The free tier
allows **20 requests per model per day per key**, which is why the pool takes a list and fails over.
Without a key the app still runs in full; only upload is unavailable.

### Development

```bash
npm run dev      # API on :4000, Vite on :5173 with hot reload
```

### Rebuilding the demo data from scratch

Only needed if you want to prove the pipeline end to end. It makes roughly ten API calls.

```bash
npm run seed                     # RFx + 30 line items + vendor rows
npm run generate:vendor-docs      # authors the five real vendor files
npm run pipeline:demo              # runs extraction against all five
npm run demo:snapshot               # freezes the result as the shipped demo database
```

## Verifying it actually works

```bash
npm test              # 70 unit tests — normalization, validation, calc engine, derivations, award logic
npm run break-tests    # 9 trust guarantees, checked against the live extracted data
```

The break-tests are the interesting ones. They assert the behaviours that separate this from a
plausible-looking dashboard: a missing item is never zero, an unspecified freight is never zero,
USD is converted with the rate disclosed, a photographed value the model was unsure about is
flagged, a vendor who answered "no" on quality is excluded but one who left a question *blank*
is only flagged, vendors are only ranked on a basket they all priced, and a question the data
cannot answer is refused rather than improvised.

## The AI provider

Google Gemini on the free tier. Which model handles what was decided by measuring extraction
accuracy against ground truth, not by preference:

| Input | Model | Measured |
|---|---|---|
| `.xlsx` `.pdf` `.docx` `.txt` | `gemini-3.5-flash-lite` | 100% price accuracy, 100% omission detection |
| `.jpg` (the photographed quote) | `gemini-3.7-flash` | 27/27 — reads the faint prices and flags them |
| Copilot + RFx drafting | `gemini-3.5-flash-lite` | — |

The photograph is the only input hard enough to need a heavier model, so it is the only call that
uses one. On the lite model that photo loses both deliberately-faint prices (25/27); `gemini-3.5-flash`
misses them too. Free-tier quota is **per model per day**, so isolating the hard case to one call
per run keeps the constrained bucket almost untouched.

All of this lives in `services/api/src/llm/client.ts` (`extractionModelFor`). Switching back to Claude
means changing that module and `extraction/extract.ts` — everything downstream is provider-agnostic.

### Multiple API keys with automatic failover

Free-tier quota is metered **per key, per model, per day**. `GEMINI_API_KEYS` takes a comma-separated
list and `services/api/src/llm/keyPool.ts` rotates through them:

- **quota error (429)** → cool that key down *for that model only* and fail over to the next key.
  A key exhausted on the vision model still gets used for the lite model.
- **transient error** (503/504, socket timeout, client abort) → back off and retry the same key; the
  service was busy, the key is fine.
- **anything else** → surface it immediately rather than burning the whole pool on a real bug.

Keys are never logged — the pool refers to them as `key2(…IB4w)`. Add more keys any time; no code
changes needed.

```bash
npm run key-status     # probes every key against every model, one cheap call each
```

When you add OpenAI or Anthropic keys, they get their own pool exposing the same `runWithFailover`
contract — nothing above that layer changes.

**If every key is exhausted**, extraction fails *safely*: nothing is deleted, the vendor keeps its
previous results, and its status is restored rather than left stuck in "processing".

**Copilot answers are cached** (`npm run warm-copilot` pre-warms the demo questions). The cache key
includes a data version derived from vendor processing state, so re-extracting any vendor
invalidates it. A cached answer was genuinely computed the first time — caching just means a live
demo doesn't hang on an API round-trip.


## Deploying

One image, one process, one port. The API serves the built front end, so there is a single URL and
nothing to install.

```bash
docker build -t aerchain .
docker run -p 4000:4000 aerchain            # works with no API key
docker run -p 4000:4000 -e GEMINI_API_KEYS=... aerchain   # plus live upload
```

`render.yaml` deploys the same image to Render's free tier. **Set `GEMINI_API_KEYS` in the host's
dashboard, never in the repository** — it is deliberately absent from the Dockerfile and from every
committed file.

The container disk is ephemeral, which is a feature here: every cold start restores the pristine
demo database, so anything a viewer changes during a session is discarded before the next one.

## Layout

```
apps/web            React + TS + Tailwind — 8 screens following the demo spine
services/api        Express + Prisma/SQLite
  src/extraction    classify → parse (5 formats) → LLM extract into a fixed schema
  src/pipeline      normalize (currency/unit) → validate (exceptions, confidence)
  src/calc          the deterministic engine — every buyer-facing number
  src/copilot       intent routing → engine → explanation, with caching
  src/award         award strategy, evidence, and what to verify before awarding
  src/metrics       impact panel + accuracy measured against ground truth
packages/shared     types, the 30-item RFx, questionnaire, FX rate, confidence bands
data/vendor-documents   the 5 generated vendor files the pipeline actually reads
```

## What the vendor documents are

Generated, not hand-waved — `npm run generate:vendor-docs` authors five real files from one
ground-truth price table, each carrying a different real-world problem:

| Vendor | Format | The problem it tests |
|---|---|---|
| A | `.xlsx` | Clean baseline, 30/30 |
| B | `.pdf` | Discount in a footnote, freight quoted separately, per-100 pricing, reworded item names |
| C | `.docx` | Priced in USD, some per-100 units, freight excluded entirely |
| D | `.jpg` | A photographed sheet — 27/30 items, two faint prices, one handwritten correction |
| E | `.txt` | An informal email — 27/30, "rest same as last year", freight extra, terms missing |

The pipeline reads these files for real. It never sees the ground-truth table — which is what makes
the extraction-accuracy figure on the Impact screen an actual measurement.
